# Файлы и исходные данные

В меню «Открыть…» поддерживаются два вида JSON. Кодек —
`src/SupplyPlanner.Infrastructure/ProjectFiles.cs`, модели —
`src/SupplyPlanner.Core/Models.cs`. Чтение проверяется до замены текущего проекта.
Неизвестные поля и некорректные значения не принимаются. Максимум файла — 4 МБ.

## Сценарий

Готовый полный шаблон: `examples/01-base.json`. Чтобы получить свою копию:

```bash
./cli.sh demo --output output/my-scenario.json
```

В корне находятся `name`, `source`, `isDemo`, `startDate`, `snapshotAt`,
`settings`, `products`, `deliveries`. Даты ISO: `2026-10-13`.
В самом окне дата поступления вводится привычно: `20.10.2026`.

| Поле | Смысл |
|---|---|
| name / source | Название и реальный источник снимка; не токен доступа |
| startDate | Дата, на начало которой задан остаток; не дата открытия файла |
| snapshotAt | Необязательная отметка времени снимка с часовым поясом |
| settings.leadDays | Доставка: 0–90 дней |
| settings.targetDays | Целевой горизонт после прибытия: 1–180 дней |
| settings.safetyDays | Страховой запас: 0–90 дней |
| settings.packSize | Размер упаковки: 1–10 000 шт. |
| settings.historyDays | Период истории: 1–60 дней |
| settings.strategy | average либо weighted |
| products[].id | Уникальный ID позиции, обычно артикул + склад |
| products[].article / name | Артикул и понятное название товара |
| products[].warehouse | Склад; null означает суммарную позицию без разбивки |
| products[].stock | Доступный остаток в штуках; null — неизвестен; 0 — известный ноль |
| products[].history[] | date, quantity в штуках, isComplete: полный ли день |
| deliveries[] | id, productId, arrivalDate, quantity, status |

`productId` поступления ссылается на `products[].id`. Количество поступления —
положительное целое. Статус — число: 0 ожидается, 1 получено, 2 отменено.
В расчёт будущих приходов входят только ожидаемые поступления; полученный товар
уже должен учитываться в остатке. Ожидаемая дата находится в интервале от начала
модели до +365 дней.

Один артикул может присутствовать на нескольких разных складах. Два одинаковых
артикула на одном складе или смешивание суммарной позиции с её же складами
запрещены: иначе возникнет двойной учёт. Не переносите суммарный спрос на каждый
склад. Нужны дневные данные по той же позиции. День без данных/неполный день
не равен известному нулевому спросу.

Прогноз использует полные дни выбранного периода перед startDate. История
не должна содержать дубли дат, будущие дни или отрицательные значения.
Сырые массивы истории могут содержать до 366 дат и быть длиннее выбранного периода;
берётся нужное окно.
Максимум сценария: 100 позиций, 500 поступлений. Поставки WB не создаются.

## Состояние приложения

«Сохранить…» создаёт файл `*.supply.json`:

```json
{
  "formatVersion": 1,
  "workspace": {
    "scenario": { "...": "полный сценарий, как выше" },
    "plan": null,
    "journal": []
  },
  "view": {
    "search": "WB-1001",
    "warehouse": "Казань",
    "status": "",
    "sort": "priority",
    "selected": "SHIRT-KZN"
  }
}
```

Это иллюстрация оболочки, не готовый импортируемый сценарий: вместо `...`
необходимы все поля сценария. Формат создаётся приложением. План намеренно
не сохраняется: он воспроизводится из исходных данных, поэтому файл не может
подменить результат устаревшим расчётом. Журнал ограничен последними 100 событиями.

Фильтры влияют на отображение и Excel, но не удаляют данные из состояния.
Настройки темы и размера окна записываются в отдельный preferences.json,
последний применённый сценарий — recovery.supply.json в пользовательской папке.
`SUPPLY_PLANNER_DATA` позволяет выбрать другую папку для изолированной проверки.

## Что не является входным файлом

- XLSX — итоговый отчёт для анализа и передачи, без всей исходной истории.
- `--output plan.json` — отчёт CLI по выбранному списку.
- CSV — в этой версии не используется.

Для возвращения к работе нужен `*.supply.json` или полный JSON-сценарий.
Встроенный пример и все examples — вымышленные данные. Автоматического экспорта
такого снимка из SellerStatus пока нет. Будущая интеграция должна сопоставить
остаток, историю и поступления по одним ID позиций и одной дате снимка.
