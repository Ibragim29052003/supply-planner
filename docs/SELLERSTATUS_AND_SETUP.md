# Установка, JSON-примеры и данные SellerStatus

## Что уже установлено на проверенном Mac

.NET SDK 10.0.400, Visual Studio Code, расширения C# и C# Dev Kit уже есть.
Для запуска через ./run.sh больше ничего устанавливать не требуется.
Зависимости Avalonia восстанавливает .NET/NuGet, а не расширение редактора.
Для готовой .app-сборки не требуются ни VS Code, ни SDK.

Чтобы редактировать XAML с подсказками и предварительным просмотром, можно
дополнительно установить [Avalonia for VSCode](https://marketplace.visualstudio.com/items?itemName=AvaloniaTeam.vscode-avalonia)
от Avalonia Team. Это необязательно для запуска. Рекомендации уже находятся
в .vscode/extensions.json; [официальная настройка IDE](https://docs.avaloniaui.net/docs/get-started/set-up-your-ide).
Не нужны MAUI workloads, WinForms/WPF, отдельный сервер или JavaScript-пакеты.
В VS Code открывайте папку supply-planner, а не соседний chat-bot-wb.

## Четыре основных JSON

Все находятся в папке examples внутри supply-planner. Это вымышленные учебные
данные. Их не скачивали из рабочего кабинета SellerStatus и они не обновляются
из сервиса. Первая строка source внутри каждого JSON это также поясняет.

| Файл | Что показывает | Ожидаемый итог |
|---|---|---:|
| [01-base.json](../examples/01-base.json) | Пять позиций, два склада, обычная доставка | 692 |
| [02-late-delivery.json](../examples/02-late-delivery.json) | Доставка занимает 12 дней, больше риск дефицита | 779 |
| [03-early-incoming.json](../examples/03-early-incoming.json) | Тот же срок, добавлен ранний приход 50 футболок в Коледино | 749 |
| [04-invalid-duplicate.json](../examples/04-invalid-duplicate.json) | Намеренно дублируется позиция для проверки валидации | Ошибка |

Запускайте по одной команде из корня проекта:

```bash
./run.sh -- --open examples/01-base.json
./run.sh -- --open examples/02-late-delivery.json
./run.sh -- --open examples/03-early-incoming.json
./run.sh -- --open examples/04-invalid-duplicate.json
```

Каждая команда запускает отдельное окно. Удобнее открыть приложение один раз
и переключать файлы кнопкой «Открыть…». Четвёртый файл должен показать ошибку,
а не заменить текущий план. При старте с ошибочным файлом остаётся встроенный пример.

Есть ещё [scenario.json](../examples/scenario.json): небольшой дополнительный
пример с одной футболкой и суммарным остатком без разбивки по складам. Он
используется в тестах; это не пятый обязательный этап показа.

```bash
./run.sh -- --open examples/scenario.json
```

Поля, даты, история и формат сохранённого проекта описаны в [DATA_FORMAT.md](DATA_FORMAT.md).
JSON — входные данные. C# проверяет их, строит прогноз, проходит остатки по дням
и рассчитывает количество и сроки поставки. Изменения в файле применяются
при повторном открытии; правки в окне — после «Рассчитать».

## Есть ли сейчас соединение с SellerStatus

Нет автоматического чтения локального или production SellerStatus, базы или API.
Планировщик самостоятельно работает с JSON и не отправляет поставки в WB.
Идея связана с практической задачей продавца в SellerStatus; обмен файлами
между сервисом и приложением ещё не реализован.

По проверенному исходному коду текущего сервиса:

- «Контроль остатков» экспортирует XLSX/PDF. Excel содержит сводку и остатки,
  суммарные заказы за 30 дней, а складская детализация находится в пояснениях.
  Это не история дневного спроса по каждой складской позиции. Выбор склада
  на этой странице отбирает товары, но показатели товара остаются суммарными.
- Карточка отдельного товара экспортирует XLSX/PDF. В XLSX есть листы «Товар»
  и «Динамика»: текущий снимок остатков и дневные заказы/продажи/возвраты.
  Эти величины не взаимозаменяемы; выручка в рублях не является спросом в штуках.
  Сам экспорт предупреждает, что полнота истории не подтверждена.
- Импортёр планировщика принимает JSON-сценарий или *.supply.json. Чтения
  SellerStatus XLSX, автоматического преобразования и отдельной кнопки
  «Экспорт в планировщик» сейчас нет. Переименование .xlsx в .json не поможет.

Это проверка исходников экспортёров, не авторизованный прогон production-кабинета.
Production-файлы и реальные данные владельца в этой проверке не использовались.

## Что можно выгрузить сейчас для подготовки реального примера

1. В SellerStatus выберите свой кабинет и откройте карточку одного товара.
2. Посмотрите дату снимка остатков и доступный период операций.
3. В меню экспорта выберите Excel (.xlsx).
4. Откройте файл: в нём должны быть «Товар» и «Динамика». Это полезный исходник
   для проектирования адаптера, но загрузить его прямо в планировщик сейчас нельзя.

Чтобы получить рабочий JSON из реальных данных, следующий этап — согласованный
экспорт сервиса либо C#-адаптер существующей выгрузки. Он должен проверить:

- один и тот же товар/склад во всех исходных таблицах;
- доступный остаток и время снимка, выбранное начало модели;
- дневной спрос в штуках, часовой пояс и полноту каждого дня;
- ожидаемые поступления с датами, если они известны. Движение товара к покупателю
  или возврат от покупателя не являются ожидаемой поставкой продавца на склад.

Если дневной спрос известен только суммарно, возможен только суммарный сценарий
warehouse=null. Нельзя скопировать общий спрос каждому складу и получить точное
распределение. Неподтверждённая история помечается неполной, отсутствие остатка —
null; программа честно вернёт отсутствие оценки. Без достаточных исходных данных
адаптер не должен обещать готовый складской план.

Реальные выгрузки и свои проекты сохраняйте в output/ или вне репозитория.
В публичные examples добавлены только вымышленные примеры.
